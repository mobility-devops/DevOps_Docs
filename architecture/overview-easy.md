# 쉽게 이해하는 아키텍처

> 원본: 노션 「쉽게 이해하는 아키텍처」에서 2026-09-30 기준으로 옮김.

> 📌 **상태: 회의 전 초안** · 기준일 2026-09-30 · 「아키텍처 개요」를 쉬운 말로 풀어쓴 해설 문서.
>
> 결정 사항과 수치의 원본은 [아키텍처 개요](overview.md). 두 문서가 다르면 「아키텍처 개요」 기준.
>
> 그림(전체 CI/CD 흐름, Kubernetes 노드·Pod 배치, VM·네트워크 배치)도 「아키텍처 개요」 2장·3장에 있음. 💡 표시는 팀 합의 전 제안.

## 1. 한 문장 요약

**택시 앱 코드를 GitHub에 올리면 검사 → 포장 → 배포 → 감시가 자동으로 이어지고, 새 버전이 이상하면 알아서 이전 버전으로 되돌아가는 시스템**을 PC 한 대 안에 만드는 프로젝트.

> 🏭 **공장에 비유하면**
>
> - **CI** = 제품 검사실. 불량품을 여기서 걸러냄.
> - **CD** = 매장 진열. 검사를 통과한 제품만 매장에 올림.
> - **모니터링** = CCTV와 경보기. 매장에 문제가 생기면 바로 알림.
> - **보안 감시(Wazuh) 💡** = 경비실. 누가 문을 억지로 따려 하거나 금고를 열면 알림.

## 2. 등장인물: 컴퓨터 7대 (+ Wazuh 도입 시 8대 💡)

실제 컴퓨터는 **호스트 PC 한 대**뿐. 그 안에 VirtualBox로 가상 컴퓨터(VM) 7대를 만듦. Wazuh를 도입하면 보안 감시용 sec-01이 더해져 8대.

| VM | 비유 | 하는 일 |
| --- | --- | --- |
| **controlnode** | 관리자 | Ansible로 나머지 VM에 프로그램 설치·설정을 한 번에 적용 |
| **ci-01** | 검사·포장 담당 | Jenkins가 코드를 테스트하고 Docker 이미지로 포장 |
| **sonar-01** | 품질 검사관 | SonarQube가 버그 가능성, 나쁜 코드 습관을 검사 |
| **k8s-master** | 매장 점장 | Kubernetes의 두뇌. 어떤 앱을 어디에 몇 개 띄울지 결정 |
| **k8s-worker1, 2** | 매장 직원 | 실제로 앱이 돌아가는 곳. 모니터링 프로그램도 여기서 실행 |
| **db-01** | 창고 | MySQL 데이터를 저장 |
| **sec-01** 💡 | 경비실 | Wazuh가 모든 VM의 보안 이벤트를 모아 공격·변조를 탐지 |

- 호스트 PC 메모리(62GiB)가 빠듯해서 VM 크기를 조금씩 줄이고(합계 41GB), 단계별로 필요한 VM만 켜는 방식을 제안 💡. 자세한 수치는 「아키텍처 개요」 3장 「자원 운영 방안」.
- VM끼리는 **192.168.56.x** 내부 전용 네트워크(Host-Only)로 통신.
- 인터넷(GitHub 등)은 VM마다 달린 별도 통로(NAT)로 나감.

## 3. 코드 한 줄을 고치면 생기는 일

「아키텍처 개요」 2장 첫 번째 그림의 번호 1~10과 같은 순서 (10번은 Wazuh 💡).

### 검사·포장 단계 (CI, 1~4)

1. 개발자가 코드를 고쳐 PR을 올림. PR 단계에서는 테스트만 실행.
2. PR이 develop에 병합되면 **Jenkins**가 감지. Jenkins가 사설망에 있어 GitHub가 직접 알릴 수 없으므로, 처음에는 Jenkins가 1~2분마다 변경 여부를 확인(폴링).
3. **SonarQube**가 코드 품질을 검사. 기준 미달이면 여기서 중단.
4. 통과하면 **Docker 이미지**(앱을 바로 실행할 수 있게 포장한 파일)를 만들고, **Trivy**로 알려진 보안 취약점을 확인한 뒤 **GHCR**(GitHub의 이미지 창고)에 저장. 이미지 이름에는 `dev-a1b2c3d`처럼 코드 버전 번호를 붙임.

### 진열 단계 (CD, 5~7)

1. Jenkins가 **gitops 저장소**에 적힌 "지금 띄울 이미지 버전"을 새 번호로 변경.
   - dev 환경: 바로 변경.
   - prod 환경: PR을 만들고 사람이 승인해야 변경.
2. **Argo CD**가 gitops 저장소를 계속 지켜보다가 "적힌 버전과 실제 버전이 다름"을 감지.
3. Argo CD가 클러스터에 새 버전을 반영. **Argo Rollouts**가 한 번에 바꾸지 않고 **Canary** 방식으로 조금씩 교체(10% → 30% → 60% → 100%).

### 운영 단계 (8~9)

1. 앱은 클러스터 밖의 **db-01**(MySQL)에서 데이터를 읽고 씀.
2. **Prometheus**가 에러율과 응답 속도를 계속 측정. 새 버전이 기준을 넘으면 **자동으로 이전 버전으로 되돌리고 Slack으로 알림.**
   - 기준: 에러율 1% 미만, 요청 100개 중 95개가 0.5초 안에 응답(p95 500ms).

### 보안 감시 단계 (10) 💡

1. 모든 VM에 설치된 **Wazuh agent**(경비원)가 로그인 기록, 파일 변경, 설치된 프로그램 목록을 sec-01(경비실)로 보냄. 위협이면 공격 IP를 차단하고 Slack으로 알림.

## 4. 사용자가 앱을 쓸 때의 경로

```text
팀원 PC → Tailscale → 호스트 PC → MetalLB IP(192.168.56.200) → Ingress → 앱 Pod → MySQL(db-01)
```

| 구성 요소 | 쉬운 설명 |
| --- | --- |
| **Tailscale** | 집이나 다른 장소에서도 이 PC 안의 VM에 접속하게 해 주는 VPN. 호스트 PC 한 곳에만 설치하면 됨. |
| **MetalLB** | 클라우드의 로드밸런서처럼 "대표 주소"를 주는 역할. VM 환경에는 로드밸런서가 없어서 MetalLB가 IP 하나(.200)를 대신 할당. |
| **Ingress** | 들어온 요청을 알맞은 앱으로 보내는 안내 데스크. HTTPS도 여기서 처리. |
| **앱 Pod** | 실제 Spring Boot 앱이 실행 중인 단위. |

## 5. 더 깊게 보기

### 5-1. Kubernetes 기본 용어

| 용어 | 쉬운 설명 | 이 프로젝트에서 |
| --- | --- | --- |
| **Node** | Kubernetes가 관리하는 컴퓨터 한 대 | k8s-master, worker1, worker2 |
| **Pod** | 앱 컨테이너가 실행되는 가장 작은 단위 | Spring Boot 앱 하나 = Pod 하나 |
| **Service** | Pod가 여러 개여도 하나의 고정 이름으로 부를 수 있게 하는 창구 | 앱 Service, DB용 `mysql` Service |
| **Rollout** | Pod를 몇 개, 어떤 버전으로 띄울지 정한 설계도. 일반 Deployment에 Canary 기능이 추가된 것 | 택시 앱 배포 방식 |
| **Namespace** | 한 클러스터 안의 칸막이 | `taxi-dev`, `taxi-prod`로 환경 분리 |
| **Probe** | 앱 건강 검진. Liveness는 "살아 있나", Readiness는 "손님 받을 준비됐나"를 확인 | 멈춘 앱은 자동 재시작, 준비 안 된 앱에는 요청을 보내지 않음 |
| **HPA** | 바쁘면 Pod 수를 늘리고, 한가하면 줄이는 자동 조절 장치 | 트래픽 급증 시연에 사용 |

**노드별 역할 (「아키텍처 개요」 2장 두 번째 그림)**

- **k8s-master(점장):** 관리만 함. 앱은 올리지 않음(taint).
- **k8s-worker1(직원 1):** 배포·네트워크 도구(Argo CD, Ingress 등) + 택시 앱.
- **k8s-worker2(직원 2):** 모니터링(Prometheus, Grafana 등) + 택시 앱.
- 택시 앱은 두 worker에 1개씩 나눠 띄움 → 한 대가 죽어도 서비스는 계속됨. 대신 모니터링은 worker2가 복구될 때까지 잠시 멈춤(의도된 설계).

### 5-2. CI를 자세히

**CI(지속적 통합)** = 코드를 합칠 때마다 자동으로 빌드·테스트해서 깨진 코드가 쌓이지 않게 하는 것.

| 순서 | 도구 | 하는 일 | 실패하면 |
| --- | --- | --- | --- |
| 1 | Gradle + Testcontainers | 테스트 실행. 실제 MySQL 8 컨테이너를 잠깐 띄워서 진짜 DB로 확인 | 중단 |
| 2 | JaCoCo | 테스트가 코드의 몇 %를 실행했는지 측정(커버리지) | SonarQube 기준에 반영 |
| 3 | SonarQube | 버그 가능성, 보안 취약 코드, 중복 코드, 커버리지 기준 검사 | Quality Gate 실패 → 중단 |
| 4 | Docker | 앱을 이미지로 포장 | 중단 |
| 5 | Trivy | 이미지 안 라이브러리·OS의 알려진 취약점 검사 | 심각도 HIGH 이상이면 중단 |
| 6 | GHCR | 통과한 이미지만 저장 | - |

- **언제 무엇을 실행하나:** PR에서는 1\~2만, develop 병합 시 1\~6 전체, main 릴리스 태그 시 `v1.0.0` 형식 이미지 생성.
- **SonarQube를 PR에서 안 돌리는 이유:** 무료판(Community)은 PR별 분석을 지원하지 않음.
- **이미지 태그에 `latest`를 안 쓰는 이유:** 지금 어떤 버전이 떠 있는지, 어느 버전으로 되돌려야 하는지 알 수 없게 됨.

### 5-3. GitOps를 자세히

**GitOps** = "서버에 무엇이 떠 있어야 하는지"를 Git 저장소에 적어 두고, Argo CD가 실제 클러스터를 그 내용과 똑같이 맞추는 방식.

> 📋 **식당 주문서에 비유하면**
>
> gitops 저장소 = 주문서, Argo CD = 주문서를 계속 확인하는 매니저.
>
> 누가 주방(클러스터)을 몰래 바꿔도 매니저가 주문서와 다른 걸 발견하고 원래대로 되돌림.
>
> 주문을 바꾸고 싶으면 주방이 아니라 **주문서(Git)를 고쳐야 함.**

**좋은 점**

- 모든 배포가 Git 커밋으로 남음 → 누가, 언제, 무엇을 바꿨는지 기록됨.
- 롤백 = Git 커밋 되돌리기.
- 클러스터를 새로 만들어도 Argo CD만 설치하면 gitops 저장소 내용대로 한 번에 복구(App of Apps).

**dev와 prod의 차이**

| 환경 | gitops 변경 방법 | 배포 방식 |
| --- | --- | --- |
| dev (`taxi-dev`) | Jenkins가 바로 push | 자동 배포 |
| prod (`taxi-prod`) | Jenkins가 PR 생성 → 사람이 승인 | Canary로 점진 배포 |

**Kustomize** = 공통 설정(base)은 하나로 두고, 환경별로 다른 부분(Pod 개수, 자원, 이미지 버전)만 덮어쓰는 도구. 같은 내용을 두 번 쓰지 않아도 됨.

### 5-4. Canary 배포를 자세히

**Canary** = 새 버전을 일부 사용자에게만 먼저 보내 보고, 괜찮으면 점점 늘리는 배포 방식. 옛날 광부들이 탄광에 카나리아를 먼저 들여보내 위험을 확인한 데서 유래.

| 단계 | 새 버전(v2)이 받는 요청 | 하는 일 |
| --- | --- | --- |
| 1 | 10% | Prometheus로 에러율·응답 속도 확인 |
| 2 | 30% | 같은 기준으로 다시 확인 |
| 3 | 60% | 같은 기준으로 다시 확인 |
| 4 | 100% | v2가 새 Stable 버전이 됨 |
| 실패 시 | 0% | 모든 요청을 v1으로 되돌림(자동 롤백) + Slack 알림 |

**주의할 점**

- **트래픽이 없으면 판정 불가:** 요청이 거의 없으면 에러율을 계산할 수 없음. 그래서 Smoke Test나 부하 생성 Job으로 일부러 요청을 만듦.
- **DB는 되돌아가지 않음:** 앱은 v1으로 돌아가도 DB 테이블 변경은 그대로 남음. 그래서 Canary 중에는 컬럼 추가처럼 v1도 문제없이 동작하는 변경(하위 호환)만 허용. 컬럼 삭제·이름 변경은 다음 릴리스로 미룸.
- **정확한 비율 조절:** 10%, 30% 같은 비율을 정확히 맞추려면 트래픽을 나눠 주는 설정(trafficRouting)이 필요. 방식은 아직 미정.

### 5-5. 네트워크를 자세히

| 네트워크 | 주소 | 쉬운 설명 |
| --- | --- | --- |
| Host-Only | 192.168.56.0/24 | 호스트 PC와 VM들만 쓰는 사내 전화망. VM끼리는 이 주소로 서로를 찾음. |
| NAT | VM마다 10.0.2.15 | VM이 인터넷에 나갈 때 쓰는 출구. 밖에서 들어오는 용도는 아님. VM마다 따로라 주소가 같아도 충돌 없음. |
| MetalLB IP | 192.168.56.200~220 | 서비스의 대표 주소. Ingress가 이 주소로 80/443 요청을 받음. |
| Pod CIDR | 10.244.0.0/16 | 클러스터 안의 Pod끼리만 쓰는 가상 주소 |
| Service CIDR | 10.96.0.0/12 | 클러스터 안의 Service끼리만 쓰는 가상 주소 |

- **Calico(CNI)** = Pod끼리 통신하게 해 주는 네트워크 플러그인. NetworkPolicy("누가 누구와 통신할 수 있나" 규칙)도 실제로 적용해 줌.
- **Tailscale Subnet Router** = 호스트 PC가 "192.168.56.x로 가려면 나를 거쳐라"라고 팀원들에게 알려 주는 것. 그래서 VM마다 Tailscale을 설치할 필요 없음.
- **K8s 노드 IP 주의:** VM에 주소가 두 개(NAT, Host-Only)라서 Kubernetes가 NAT 주소(10.0.2.15)를 잘못 잡을 수 있음. 반드시 Host-Only 주소로 지정.

### 5-6. DB 연결을 자세히

- MySQL은 클러스터 **밖** db-01에 있음. 스키마는 `taxi_dev`, `taxi_prod`로 분리.
- 앱은 IP 대신 클러스터 안의 이름 `mysql`로 접속. 이 이름은 selector 없는 Service가 db-01 주소로 연결해 줌 → DB 주소가 바뀌어도 앱 설정은 그대로.
- DB 아이디·비밀번호는 환경변수(`DB_USERNAME`, `DB_PASSWORD`)로 전달. 코드에는 절대 넣지 않음.
- DB 문은 두 겹으로 잠금:
  - **db-01 방화벽:** 3306은 worker 2대와 호스트만 허용. Pod가 밖으로 나갈 때는 노드 주소로 바뀌어 나가서, db-01 입장에서는 어느 Pod인지 모르고 worker만 보임.
  - **클러스터 안 규칙(NetworkPolicy) 💡:** 그래서 클러스터 안에서 "앱 Pod만 DB로 나갈 수 있음"을 한 번 더 제한.
- Flyway = 테이블 변경 내역을 `V1__...sql`, `V2__...sql`처럼 순서대로 기록하고, 앱이 시작할 때 아직 적용 안 된 것만 자동 적용하는 도구.

### 5-7. 모니터링을 자세히

| 도구 | 비유 | 하는 일 |
| --- | --- | --- |
| Actuator + Micrometer | 앱의 체온계 | 앱이 요청 수, 에러 수, 응답 시간을 숫자로 내보냄 |
| Prometheus | 기록원 | 앱·노드·DB의 숫자를 주기적으로 모아 저장. Canary 판정에도 사용 |
| Grafana | 상황판 | 모은 숫자와 로그를 그래프·대시보드로 표시 |
| Loki + Promtail | 일지 보관소 | 각 Pod의 로그를 모아 검색 가능하게 함 |
| Alertmanager | 경보 담당 | 문제 조건에 걸리면 정리해서 Slack으로 전송 |
| mysqld_exporter | DB 체온계 | MySQL 상태(연결 수, 쿼리 수)를 Prometheus가 읽을 수 있게 내보냄 |

**목표 수치(SLO)**

- **가용성 99%:** 30일 동안 요청 100개 중 99개 이상은 서버 오류(5xx) 없이 응답.
- **p95 500ms:** 요청 100개 중 95개는 0.5초 안에 응답.
- **p99 1초:** 요청 100개 중 99개는 1초 안에 응답(참고용).

**알림 예시:** Pod 재시작 반복, 에러율 급증, MySQL 다운, 디스크 80% 초과, DB 연결 80% 초과.

### 5-8. 인프라 자동화를 자세히

- **Vagrant** = VM을 코드(Vagrantfile)로 만드는 도구. VM을 같은 설정으로 만들고, `vagrant up <이름>` / `vagrant halt <이름>`으로 필요한 VM만 켜고 끔 💡.
- **Ansible** = 여러 서버에 같은 설정을 SSH로 한 번에 적용하는 도구. 시간대, swap 해제, 보안 설정, Kubernetes 설치 등을 코드로 관리.
- **좋은 점:** VM이 망가져도 명령 몇 번으로 똑같이 다시 만들 수 있음(재현성).

### 5-9. 보안과 백업을 자세히

**비밀번호 관리**

| 위치 | 방법 |
| --- | --- |
| Kubernetes | **Sealed Secrets**: 비밀번호를 암호화해서 Git에 저장. 클러스터 안의 컨트롤러만 풀 수 있어 저장소가 노출돼도 안전 |
| Jenkins | **Jenkins Credentials**: GitHub·GHCR 토큰을 Jenkins 안에 보관 |
| Ansible | **ansible-vault**: 설정 파일 안의 비밀번호를 암호화 |

**접속 보안:** SSH는 비밀번호 대신 키로만 로그인, 반복 로그인 실패는 fail2ban이 차단.

**Wazuh 💡:** fail2ban은 VM 한 대의 문 앞 자물쇠, Wazuh는 모든 VM을 한 화면에서 보는 건물 전체 보안 시스템. Trivy는 배포 전 Docker 이미지를, Wazuh는 운영 중인 VM 자체를 검사해서 서로 보완.

**인터넷 노출 주의 💡:** 나중에 Webhook을 위해 Tailscale Funnel을 쓰면 Jenkins가 인터넷에 열림. webhook 경로만 공개하고, 비밀 키(webhook secret)로 진짜 GitHub 요청인지 확인.

**백업**

- MySQL: 매일 전체 백업 + binlog(변경 기록)로 특정 시점까지 복구 가능.
- Jenkins 설정: 매일, etcd(클러스터 상태): 6시간마다.
- 모든 VM이 한 PC의 한 SSD에 있으므로 **주 1회 외장 디스크로 복사.**
- 목표: 데이터 손실 24시간 이내, 복구 1시간 이내. 복구 연습(리허설)도 정기적으로 실시.

## 6. 왜 이렇게 나눴나

| 결정 | 이유 |
| --- | --- |
| CI를 클러스터 밖에 둠 | 빌드와 품질 검사는 메모리를 많이 씀. 앱과 같이 두면 서로 느려지고, 클러스터가 고장 나면 CI도 멈춤. |
| Jenkins와 SonarQube 분리 | SonarQube는 내부 검색 엔진 때문에 메모리를 많이 씀. 같은 VM이면 빌드가 느려짐. |
| DB를 별도 VM에 둠 | 클러스터를 부쉈다가 다시 만들어도 데이터는 그대로 남음. |
| worker 2대 | 한 대를 꺼도 서비스가 살아 있는 모습과 Canary 배포를 시연 가능. |
| Vagrant + Ansible | VM이 망가져도 명령 한 번으로 똑같이 다시 생성 가능. |
| Wazuh를 별도 VM에 둠 💡 | Wazuh는 메모리를 많이 씀. 클러스터 안에 두면 앱과 자원을 다투고, 클러스터가 고장 나면 감시도 같이 멈춤. |

## 7. 알아 둘 한계

- **PC가 꺼지면 서비스 전체가 멈춤.** 모든 VM이 한 PC 안에 있기 때문. 팀 회의에서 합의할 안건.
- **Control Plane(k8s-master)은 1대.** master가 고장 나면 새 배포는 멈춤. 대신 etcd 스냅샷으로 복구.
- **호스트가 Wi-Fi에 의존.** 연결이 끊기면 이미지 다운로드 실패. 가능하면 유선 사용.
- **호스트 메모리가 빠듯함.** VirtualBox는 VM이 쓴 메모리를 호스트에 돌려주지 않아서, VM을 모두 켜면 호스트가 느려질 수 있음. 그래서 VM 크기를 줄이고 필요할 때만 켬 💡.

## 9. 용어 한눈에 보기

| 용어 | 한 줄 설명 |
| --- | --- |
| CI | 코드를 합칠 때마다 자동 빌드·테스트 |
| CD | 검사를 통과한 버전을 자동으로 서버에 배포 |
| Docker 이미지 | 앱과 실행 환경을 한 덩어리로 포장한 파일 |
| GHCR | GitHub의 Docker 이미지 저장소 |
| GitOps | 서버 상태를 Git에 적어 두고 그대로 맞추는 방식 |
| Argo CD | Git 내용과 클러스터를 비교해 맞춰 주는 도구 |
| Argo Rollouts | Canary처럼 조금씩 배포하고 자동 롤백하는 도구 |
| Canary | 새 버전을 일부에게만 먼저 보내 보는 배포 |
| 롤백 | 이전 버전으로 되돌리기 |
| Smoke Test | 배포 직후 핵심 기능이 동작하는지 빠르게 확인하는 테스트 |
| Quality Gate | SonarQube의 합격 기준 |
| p95 | 요청 100개 중 95번째로 느린 응답 시간 |
| SLO | 서비스가 지켜야 할 품질 목표 |
| Runbook | 장애가 났을 때 따라 할 대응 절차서 |
| Wazuh | 모든 서버의 보안 이벤트를 모아 공격을 탐지·대응하는 보안 도구(SIEM) |
| taint | 특정 노드에 일반 Pod가 올라가지 못하게 막는 표시 (master에 사용) |
