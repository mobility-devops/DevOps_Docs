> 원본: 노션 「쉽게 이해하는 로드맵」에서 2026-09-30 기준으로 옮김.

> 📌 **상태: 회의 전 초안** · 기준일 2026-09-30 · 「로드맵과 할 일」을 쉬운 말로 풀어쓴 해설 문서.
> 작업 목록과 완료 기준의 원본은 [로드맵과 할 일](plan.md). 두 문서가 다르면 「로드맵과 할 일」 기준.
> 각 기술의 뜻은 [쉽게 이해하는 아키텍처](../architecture/overview-easy.md) 참고.

## 1. 한 문장 요약

**설계는 거의 끝났고, 이제 VM 만들기부터 시작해 7단계에 걸쳐 CI/CD 시스템을 한 층씩 쌓아 올리는 계획.** 앱(백엔드) 기능은 이미 완성된 상태라, 인프라를 만드는 동안 앱은 배포 준비만 하면 됨.

> 🏠 **집 짓기에 비유하면**
>
> - 0단계 = 설계도 확정
> - 1단계 = 땅 고르기와 기초 공사 (VM)
> - 2단계 = 뼈대와 배관 (Kubernetes, DB)
> - 3단계 = 자재 검사실 (CI)
> - 4단계 = 자동 배송 시스템 (GitOps, CD)
> - 5단계 = CCTV와 화재경보기 (모니터링, 알림)
> - 6단계 = 시범 입주 (Canary 배포)
> - 7단계 = 보험 가입과 안전 점검 (백업, 보안, 장애 시연, Wazuh 경비실 💡)
>
> 기초 없이 벽을 올릴 수 없듯이, 앞 단계가 끝나야 다음 단계를 시작할 수 있음.

## 2. 지금 어디쯤인가

| 트랙 | 상태 | 쉽게 말하면 |
|---|---|---|
| 앱 (백엔드) | v1 기능 전부 완료 (develop 병합) | 택시 호출부터 완료·취소까지 동작하는 앱은 완성. 이제 "서버에 올릴 수 있게" 포장만 남음 |
| 인프라 | 0단계 (준비) 진행 중 | 현재 환경 조사와 설계는 끝남. VM을 만들기 전에 몇 가지 결정만 남음 |

```text
[0 준비] → 1 VM → 2 K8s·DB → 3 CI → 4 GitOps → 5 모니터링 → 6 Canary → 7 운영 마무리
   ▲
 지금 여기
```

## 3. 단계별 쉬운 설명

### 0단계. 준비 (진행 중)

- **하는 일:** VM을 만들기 전에 꼭 필요한 결정을 내림. 가장 중요한 것은 **SSH 키**와 **로그인 사용자명**.
- **왜 먼저 하나:** VM을 만들 때 이 정보를 넣어야 해서, 나중에 바꾸면 VM을 다시 만들어야 함.
- **함께 정할 것 💡:** VM 자원 조정안(합계 41GB, 단계별 기동), Wazuh 도입 여부, 문서 원본 위치.
- **끝났다는 기준:** 1단계를 바로 시작할 수 있을 만큼 결정이 끝난 상태.

### 1단계. VM 기반 (기초 공사)

- **하는 일**
  - 호스트 PC에 Vagrant 설치 확인.
  - 쓰지 않는 기존 VM 정리.
  - Vagrantfile(VM 설계도 파일)에 신규 VM을 정의(Wazuh 도입 시 sec-01 포함 💡).
  - 호스트 PC 메모리가 빠듯해서 처음에는 필요한 VM(k8s 3대, db-01)만 켬. 나머지는 필요한 단계에서 켬 💡.
  - controlnode는 Ansible만 돌리므로 RAM을 2GB로 줄임 💡.
  - controlnode에 Ansible 설치, 모든 VM에 공통 설정 적용(시간 동기화, SSH 보안, 로그인 공격 차단).
  - 호스트 PC에 Tailscale Subnet Router 설정 → 팀원이 밖에서도 VM에 접속 가능.
- **끝났다는 기준 (쉽게):** `vagrant up` 한 번으로 기본 VM(k8s 3대, db-01)이 켜지고, controlnode에서 `ansible all -m ping`(모든 VM에 "살아 있니?" 확인)이 전부 성공.
- **결과물:** DevOps_Infra 저장소의 Vagrantfile, Ansible 인벤토리(VM 목록), 공통 설정 코드.

### 2단계. Kubernetes와 DB (뼈대와 배관)

- **하는 일**
  - 3대의 VM(master 1, worker 2)을 하나의 Kubernetes 클러스터로 묶음.
  - 클러스터 필수 부품 설치: Calico(Pod끼리 통신), MetalLB(대표 IP), Ingress-NGINX(요청 안내), cert-manager(HTTPS 인증서), local-path-provisioner(저장 공간), metrics-server(자동 확장 HPA에 필요).
  - 노드 역할 정하기: worker1은 배포·네트워크 도구, worker2는 모니터링, master에는 앱을 올리지 않음.
  - db-01에 MySQL 8 설치: 스키마·계정 생성, 방화벽, 백업 스크립트, 상태 측정 도구(mysqld_exporter).
- **끝났다는 기준 (쉽게)**
  - 노드 3대가 모두 Ready(준비 완료).
  - 샘플 앱에 HTTPS로 접속 가능.
  - worker에서 DB 접속은 되고, 허용 안 된 곳에서는 막힘.
  - 백업한 DB를 실제로 복구해 보는 연습 1회 성공.

### 3단계. CI (자재 검사실)

- **하는 일**
  - ci-01·sonar-01을 켜고, ci-01에 Jenkins, sonar-01에 SonarQube 설치. 자바 프로그램이 메모리를 다 쓰지 않도록 상한을 걸어 둠 💡.
  - GitHub·GHCR 접근용 토큰 발급 후 Jenkins에 등록.
  - 파이프라인 작성: PR은 테스트 → 커버리지, develop 병합은 여기에 품질 검사 → 이미지 빌드 → 보안 스캔 → GHCR 저장까지.
  - 백엔드 저장소에 Dockerfile(포장 방법)과 Jenkinsfile(검사 순서) 추가.
- **사전 조건:** 앱이 빌드·테스트 가능한 상태 → 이미 충족.
- **끝났다는 기준 (쉽게):** develop에 병합하면 이미지가 GHCR에 자동으로 올라가고, 품질 기준 미달이면 중간에 멈춤.

### 4단계. GitOps와 CD (자동 배송)

- **하는 일**
  - gitops 저장소 만들기: 공통 설정(base)과 환경별 설정(dev, prod) 분리.
  - Argo CD 설치, dev·prod 공간(namespace) 생성, 비밀번호 암호화 도구(Sealed Secrets) 설치.
  - Jenkins가 새 이미지 버전을 gitops에 기록하도록 연결: dev는 바로, prod는 PR로.
- **끝났다는 기준 (쉽게):** develop에 병합하면 dev 서버에 자동 배포, prod는 사람이 승인해야만 배포, Git 커밋을 되돌리면 이전 버전으로 복귀.

### 5단계. 모니터링과 알림 (CCTV와 경보기)

- **하는 일**
  - Prometheus·Grafana·Alertmanager 묶음(kube-prometheus-stack) 설치. 로그 수집(Loki)은 메모리 여유를 확인한 뒤 마지막에 설치 💡.
  - Grafana 대시보드 구성(목표 수치 SLO 포함), Slack 알림 연결, 장애 대응 절차서(Runbook) 초안 작성.
- **끝났다는 기준 (쉽게):** 앱·DB·서버 상태가 그래프로 보이고, 테스트 알림이 Slack에 도착.

### 6단계. Canary 배포 (시범 입주)

- **하는 일**
  - 일반 배포(Deployment)를 Canary 배포(Rollout)로 교체.
  - 판정 규칙(AnalysisTemplate) 작성: 에러율과 응답 속도(p95) 기준.
  - 배포 직후 기본 동작 확인(Smoke Test)과 가짜 요청을 만드는 부하 생성 준비.
- **왜 5단계 다음인가:** Canary는 Prometheus 지표를 보고 판정하므로 모니터링이 먼저 있어야 함.
- **끝났다는 기준 (쉽게):** 정상 버전은 10% → 100%로 알아서 진행, 일부러 오류를 넣은 버전은 알아서 되돌아감(시연).

### 7단계. 운영 마무리 (보험과 안전 점검)

- **하는 일**
  - 백업 자동화, 외장 디스크로 정기 복사, 복구 연습 정례화.
  - 권한 최소화(RBAC), Pod 보안 규칙, 통신 제한(NetworkPolicy), 자원 한도(ResourceQuota) 적용.
  - 장애 시나리오 시연: DB 다운, 배포 롤백.
  - Wazuh 도입 시 💡: 경비실 VM(sec-01)을 켜고 모든 VM에 경비원(agent)을 배치. SSH 공격 탐지 같은 보안 시연 1~2건.
  - 설계 결정 기록(ADR)과 장애 대응 절차서(Runbook) 정리, 최종 문서를 docs 저장소에 반영.
- **끝났다는 기준 (쉽게):** 복구 연습 통과, 장애 시연 2건 완료, 문서가 최신 상태.

## 4. 앱은 언제 무엇을 준비하나

앱 기능은 완성 상태. 인프라 단계에 맞춰 "배포 준비" 작업만 순서대로 하면 됨.

| 언제까지 | 준비할 것 | 왜 필요한가 |
|---|---|---|
| 3단계(CI) 전 | DB 접속 주소를 환경변수로 받게 변경 | 지금은 `localhost`로 고정되어 있어 서버에서는 DB를 못 찾음 |
| 3단계(CI) 전 | Dockerfile, Jenkinsfile, Testcontainers·JaCoCo | 이미지 포장 방법과 CI 검사 순서, 실제 MySQL 테스트와 커버리지 측정 |
| 5단계(모니터링) 전 | Actuator·Micrometer | 앱이 요청 수·에러 수·응답 시간을 Prometheus에 내보내야 감시 가능 |
| 6단계(Canary) 전 | Canary용 v2 (정상 버전 + 일부러 오류를 넣은 버전) | "좋은 버전은 진행, 나쁜 버전은 자동 롤백"을 시연하기 위해 |

## 5. 지금 정해야 할 것 (결정 대기)

| 항목 | 추천 | 쉬운 설명 |
|---|---|---|
| VM에 넣을 SSH 공개키 | 전용 키를 새로 생성 | SSH 키는 자물쇠(공개키)와 열쇠(비밀키) 한 쌍. 자물쇠는 VM에 달아도 되지만 열쇠는 절대 공유 금지 |
| VM 로그인 사용자명, sudo | 사용자명 `devops`, sudo 비밀번호 없음 | Ansible이 자동으로 관리자 명령을 실행하려면 매번 비밀번호를 묻지 않아야 함 |
| controlnode → 새 VM 접속 키 | controlnode 전용 키를 만들어 배포 | 관리자(controlnode)가 다른 VM에 들어갈 열쇠를 따로 가짐. Vagrant가 VM 생성 시 자물쇠를 달아 줌 |
| DevOps_Infra 브랜치 규칙 | docs 저장소와 동일 | main + 작업 브랜치, PR, Squash and merge. main 브랜치부터 만들어야 함 |
| 인프라 작업 Issue 초안 | 작성 | 초안은 Claude가 작성, GitHub Issue 생성은 사용자가 직접 |
| 노션·`CLAUDE.md` 갱신 시점 | VM·K8s가 뜬 뒤 한 번에 | 실제로 만들어 보고 달라진 점까지 한 번에 반영하는 편이 효율적 |
| 백엔드와 인프라 진행 순서 | 인프라 1~2단계 먼저 | 앱은 3단계에서 필요하므로, 그 전까지 인프라 기초를 먼저 쌓음 |

## 7. 사용자가 직접 해야 할 일

Claude는 클라우드에서 실행되어 호스트 PC, VirtualBox, 노션 페이지 삭제, GitHub 설정에 직접 손댈 수 없음. 그래서 아래 작업은 직접 진행.

| 할 일 | 이유 |
|---|---|
| DevOps_Docs PR을 Squash and merge | 현재 환경 문서를 docs 저장소에 확정 반영 |
| DevOps_Docs 기본 브랜치를 main으로 변경, docs/env-status 브랜치 삭제 | 저장소 정리 |
| 노션 옛 페이지 「개발 환경 현황 (호스트 PC + VirtualBox)」 삭제 | 같은 정보가 두 곳에 있으면 혼란 |
| 호스트에서 `vagrant --version` 확인 | 1단계의 첫 작업. 없으면 설치 |
| controlnode RAM을 2GB로 변경 💡 | 기존 VM이라 Vagrant가 아니라 VirtualBox에서 직접 변경 |
| VM을 많이 켤 때 호스트의 로컬 MySQL·Docker·Java 앱 종료 | 호스트 메모리 약 3~5GB 확보(추정) |
| 전용 SSH 키 생성 후 공개키 전달 | VM 생성에 필요 (0단계 결정 사항) |
| 3단계 전에 GitHub App과 토큰 생성 | Jenkins가 GitHub·GHCR에 접근하기 위한 권한 |
| 7단계 이후 백업을 외장 디스크로 정기 복사 | PC 디스크가 고장 나도 데이터가 남도록 |

## 8. 조심해야 할 점 (리스크)

| 리스크 | 무슨 일이 생기나 | 대응 |
|---|---|---|
| PC 한 대에 모든 VM | PC가 꺼지면 서비스 전체 중단, 디스크 고장 시 백업까지 유실 | 외장 디스크 정기 복사, 시연 시간에만 가동 |
| RAM·CPU 부족 | VM을 모두 켜면 호스트 PC 메모리가 거의 차서 전체가 느려짐 | VM 크기 조정(합계 41GB), 필요한 VM만 켜기, 메모리 상한 설정 💡 |
| 호스트가 Wi-Fi 사용 | 연결이 끊기면 이미지 다운로드 실패 | 가능하면 유선 연결 |
| Vagrant와 VirtualBox 7.2 호환 | VM 생성 실패 가능 | Vagrant 최신 버전 설치 |
| 무료 GitHub 조직의 제한 | main에 직접 push를 기술적으로 막을 수 없음 | 팀 약속 + Jenkinsfile 로직으로 보완 |
| Jenkins가 사설망에 있음 | GitHub가 Jenkins에 직접 알림 불가 | 폴링으로 시작, 이후 Tailscale Funnel 검토 |
| 기술 범위가 넓음 | 일정 지연 | 단계별 완료 기준으로 관리, 보류 기술 명시 |
| 팀 문서와 초안 불일치 | 팀 문서는 MariaDB·Discord, 초안은 MySQL 8·Slack → 팀원마다 다른 기준으로 작업할 위험 | 회의에서 기준 문서 확정 후 팀 문서 갱신 |

## 9. 용어 한눈에 보기

| 용어 | 한 줄 설명 |
|---|---|
| Vagrantfile | VM을 어떻게 만들지 적은 설계도 파일 |
| Ansible 인벤토리 | Ansible이 관리할 서버 목록 |
| role | Ansible 설정 묶음 (예: common = 모든 VM 공통 설정) |
| Ready | Kubernetes 노드가 일을 받을 준비가 된 상태 |
| local-path-provisioner | 노드의 디스크를 Pod 저장 공간으로 빌려주는 도구 |
| JCasC | Jenkins 설정을 화면 클릭 대신 코드 파일로 관리하는 방식 |
| AnalysisTemplate | Canary 판정 규칙 (어떤 지표가 얼마 이하여야 통과인지) |
| Smoke Test | 배포 직후 핵심 기능이 동작하는지 빠르게 확인하는 테스트 |
| RBAC | 사람·프로그램별로 할 수 있는 일을 최소한으로 제한하는 권한 관리 |
| ResourceQuota | namespace별 CPU·메모리 사용 한도 |
| ADR | "왜 이 기술을 골랐나" 같은 설계 결정 기록 |
| Runbook | 장애가 났을 때 따라 할 대응 절차서 |
